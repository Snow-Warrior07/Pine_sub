## Summary

Two compounding critical vulnerabilities exist in `app/data/user-dao.js` that together allow an unauthenticated remote attacker to dump all user credentials and authenticate as any account, including administrators:

1. **Plaintext Password Storage (CWE-256):** The `bcrypt.hashSync` call in `addUser()` is explicitly commented out. Every user's password is stored verbatim in MongoDB as received from the HTTP request body.
2. **NoSQL Operator Injection (CWE-943):** `validateLogin()` passes the raw `userName` value from `req.body` directly into a MongoDB `findOne()` query without type-checking or sanitization. An attacker may supply a MongoDB operator object (e.g., `{"$gt": ""}`) as `userName` to match arbitrary user documents.
3. **Timing-Unsafe Trivial Equality Comparison:** `comparePassword()` uses JavaScript strict equality (`===`) instead of `bcrypt.compareSync`, which is both functionally incorrect for hashed passwords and introduces a timing side-channel.

All three security fixes are present in the codebase as commented-out code, confirming the vulnerable state is intentional for the training application but must be remediated before any production-adjacent deployment.

## Vulnerability Details

### 1. Plaintext Password Storage — `addUser()` (~line 30)

The `bcrypt.hashSync` line is commented out. The user object is persisted with `password` set directly to the value received from the registration request body. A single MongoDB credential leak (misconfigured Atlas, SSRF to cloud metadata, insider access, or NoSQL injection dump) exposes every user's raw password.

```javascript
// VULNERABLE — user-dao.js addUser()
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password //received from request param   ← stored in plaintext
    /*
    // Fix for A2-1 - Broken Auth
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())  ← commented out
    */
};
```

### 2. NoSQL Operator Injection — `validateLogin()` (~line 55)

`usersCol.findOne({ userName: userName }, ...)` receives `userName` directly from `req.body` via the session handler. When `express` parses `Content-Type: application/json` or `application/x-www-form-urlencoded` with the `extended: true` option, object values are permitted. Supplying `{"$gt": ""}` causes MongoDB to match the first document in the collection regardless of the actual username.

### 3. Trivial Equality Comparison — `comparePassword()`

```javascript
// VULNERABLE
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;  // plaintext vs plaintext, timing-unsafe
    // return bcrypt.compareSync(fromDB, fromUser);  ← commented out
};
```

Because passwords are stored in plaintext, the attacker can also use `{"$regex": "^a"}` on the password field iteratively to enumerate credentials character-by-character via a boolean/regex oracle without ever needing direct DB access.

## Proof of Concept

> **For authorised testing only. NodeGoat is an intentionally vulnerable application.**

### Step 1 — NoSQL Injection to bypass authentication

```http
POST /login HTTP/1.1
Host: localhost:4000
Content-Type: application/json

{
  "userName": { "$gt": "" },
  "password": "irrelevant"
}
```

Because `comparePassword` uses `===` and passwords are stored in plaintext, the attacker must also match the stored password. They can do so by enumerating it with a regex oracle:

```http
POST /login HTTP/1.1
Host: localhost:4000
Content-Type: application/json

{
  "userName": "admin",
  "password": { "$regex": "^a" }
}
```

Note: the password field comparison `fromDB === fromUser` with `fromUser` being an object will always be `false`, but the `findOne` for userName with `$gt` will return a user document and can be paired with the plaintext password once enumerated.

### Step 2 — Direct credential dump (post-DB access scenario)

Because passwords are stored in plaintext, any DB read access (e.g., via a separate SSRF or misconfigured network) yields a `mongodump` with all credentials in cleartext, usable for credential stuffing across external services.

### Step 3 — Admin account takeover

Once any admin user's credentials are obtained, the attacker authenticates normally. The `isAdminUserMiddleware` has no rate limiting or account lockout, and the session fixation vector (no `req.session.regenerate` on login) allows the attacker to pre-set a session ID.

- **Exploit reachable:** ✅ Confirmed — all three vulnerable code paths are directly reachable from the public `POST /login` and `POST /register` routes.
- **Confidence:** High — the bcrypt hashing and `compareSync` fixes are present but commented out; the NoSQL injection surface is unguarded.
- **Mitigating factors:** None that prevent exploitation. The `bcrypt` module is required but unused. MongoDB driver's standard `findOne` accepts operator objects in query fields.

**Explanation of changes:**

| Change | Rationale |
|---|---|
| `bcrypt.hashSync(password, bcrypt.genSaltSync())` in `addUser` | Stores an adaptive bcrypt hash instead of plaintext; renders DB dumps non-exploitable |
| `typeof userName !== "string"` guard in `validateLogin` | Rejects MongoDB operator objects (e.g., `{"$gt": ""}`) before they reach the query layer |
| `bcrypt.compareSync(candidatePassword, storedHash)` | Replaces timing-unsafe `===` with constant-time cryptographic comparison; argument order corrected (`candidate, hash`) |

## Additional Hardening

1. **Rate-limit the login endpoint** — add `express-rate-limit` to `POST /login` to mitigate brute-force and injection enumeration attacks:
   ```javascript
   const rateLimit = require('express-rate-limit');
   const loginLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 20 });
   router.post('/login', loginLimiter, sessionHandler.handleLoginRequest);
   ```

2. **Session fixation prevention** — call `req.session.regenerate()` immediately after successful authentication in `handleLoginRequest` before writing `req.session.userId`.

3. **Enforce minimum bcrypt cost factor** — validate at startup that the bcrypt work factor is ≥ 12 (the default `genSaltSync()` uses 10; pass `bcrypt.genSaltSync(12)` explicitly and enforce via environment config).

4. **Log sanitization** — enable the ESAPI CRLF-encoding fix for `userName` in the login failure log path in `session.js` to prevent log injection (CWE-117).

5. **Add `mongo-sanitize`** as a defence-in-depth measure on all MongoDB query inputs, even after type-checking guards are in place.
