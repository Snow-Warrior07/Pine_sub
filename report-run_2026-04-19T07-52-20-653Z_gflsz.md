## Summary

All user passwords are stored **in plaintext** inside MongoDB. The bcrypt hashing call in `addUser()` is explicitly commented out, and the `comparePassword()` helper in `validateLogin()` uses strict string equality (`===`) rather than a constant-time `bcrypt.compareSync()` comparison. Any attacker who achieves read access to the `users` collection — trivially reachable via the co-located NoSQL injection flaw in `validateLogin()`, a misconfigured MongoDB instance, or any other database-read primitive — immediately obtains every user's plaintext credential with **zero cracking effort**. Admin account takeover and cross-service credential-stuffing follow directly.

---

## Vulnerability Details

### 1. Plaintext Password Written to MongoDB (`addUser`)

```js
// app/data/user-dao.js — lines ~24-30 (current vulnerable state)
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password //received from request param   ← raw, unhashed string stored to DB
    /*
    // Fix for A2-1 - Broken Auth  ← NEVER UNCOMMENTED
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())
    */
};
```

The secure alternative is present in the codebase but permanently disabled. Every `INSERT` into the `users` collection writes the password exactly as received from the HTTP request body.

### 2. Plaintext Equality Check at Authentication (`validateLogin`)

```js
// app/data/user-dao.js — lines ~44-50 (current vulnerable state)
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;  // ← direct string comparison, no bcrypt, no constant-time
    /*
    // Fix for A2-Broken Auth  ← NEVER UNCOMMENTED
    return bcrypt.compareSync(fromDB, fromUser);
    */
};
```

Because the stored value is plaintext and the comparison is a simple `===`, there is:
- **No hash barrier** — credentials are trivially readable.
- **No constant-time guarantee** — V8 string equality short-circuits on first mismatch, leaving a timing side-channel.
- **No upgrade path** — bcrypt is imported but never exercised on the active code path.

## Proof of Concept

> The following assumes an attacker has obtained a MongoDB dump via the co-located NoSQL injection in `validateLogin()` or via an unauthenticated MongoDB port (default NodeGoat configuration).

```bash
# 1. Connect to the unauthenticated MongoDB instance (default NodeGoat setup)
mongosh "mongodb://localhost:27017/nodegoat"

# 2. Dump the users collection — passwords are in cleartext
db.users.find({}, { userName: 1, password: 1, isAdmin: 1 })
# Output example:
# { _id: 1, userName: 'admin',  password: 'Admin_123', isAdmin: true  }
# { _id: 2, userName: 'user1',  password: 'password1', isAdmin: false }
# { _id: 3, userName: 'user2',  password: 'hunter2',   isAdmin: false }

# 3. Authenticate as admin with harvested cleartext credential — no cracking required
curl -s -c jar.txt -X POST http://localhost:4000/login \
  -d 'userName=admin&password=Admin_123'
# → 302 redirect to /dashboard — full admin session obtained

# 4. Credential-stuff harvested passwords against external services
# (Email, GitHub, banking — high success rate due to password reuse)
```

The `comparePassword()` equality check means the stolen plaintext value authenticates directly without any transformation.

## Validation

**Confidence: High.** The exploit path is fully confirmed by static analysis:

- `addUser()` contains `password //received from request param` as the active assignment; the `bcrypt.hashSync` line is inside a block comment.
- `comparePassword()` returns `fromDB === fromUser`; the `bcrypt.compareSync` line is inside a block comment.
- `bcrypt-nodejs` is required at the top of the file, confirming the library is available but intentionally bypassed.
- `usersCol.insert(user, ...)` is called with the plaintext-containing document — no pre-insert hook or middleware transforms the value.
- No server-side middleware (confirmed by reviewing `session.js` and the DAO layer) applies any hashing transformation.

**Mitigating factors (minor):**
- MongoDB may have network ACLs restricting direct external access.
- A secondary read primitive (NoSQL injection or misconfiguration) is required to bulk-extract credentials.
- NodeGoat is a training application — hardening controls are intentionally absent, meaning real-world deployments based on this code inherit all vulnerabilities.

## Remediation

**Post-patch behaviour:**
- `addUser()` generates a unique salt (cost factor 12) per registration and stores only the bcrypt hash.

- Existing plaintext-password accounts will fail authentication after the patch. A **one-time migration** (prompt users to reset passwords on next login) is required for production deployments.

## Additional Hardening

1. **Migrate away from `bcrypt-nodejs`** — this package is unmaintained (last release 2014). Replace with [`bcrypt`](https://www.npmjs.com/package/bcrypt) (native bindings) or [`argon2`](https://www.npmjs.com/package/argon2) (OWASP-recommended winner of PHC).

2. **Sanitize `userName` before MongoDB query** — `usersCol.findOne({ userName })` passes unsanitized user input directly to MongoDB, enabling NoSQL injection (`{"$gt": ""}` style payloads). Apply strict allowlist validation (e.g., `/^[a-zA-Z0-9_]{3,32}$/`) before the query.

3. **Enforce password policy at registration** — minimum length (≥ 12 characters), reject common passwords (HaveIBeenPwned API or local blocklist) to reduce offline-cracking risk even with bcrypt in place.

4. **Remove sensitive values from error paths** — `console.log("Error: attempt to login with invalid user: ", userName)` logs raw user input, enabling CRLF log-injection. Encode the value with an ESAPI-equivalent encoder or strip newlines before logging.
