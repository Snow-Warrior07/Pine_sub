## Summary

Two critical, independently exploitable vulnerabilities exist in `app/data/user-dao.js`:

1. **Plaintext Password Storage (CWE-256):** `addUser()` stores the raw plaintext password in MongoDB. The bcrypt hashing call (`bcrypt.hashSync`) is explicitly commented out. Any read access to the database — backup file, secondary injection, misconfigured MongoDB exposure — immediately yields every user's usable cleartext credential with zero cracking effort.

2. **NoSQL Injection in `validateLogin()` (CWE-943):** The `userName` parameter from `req.body` is passed without type-checking directly into `usersCol.findOne({ userName: userName })`. Express with `body-parser` deserializes JSON bodies, so a caller may supply a MongoDB query operator object (e.g., `{"$gt": ""}`) as the value. Combined with the plaintext password storage, this allows username enumeration and, under certain conditions, authentication bypass.

The `comparePassword()` helper further compounds the issue by using a direct strict-equality check (`===`) rather than `bcrypt.compareSync()`, which would be vulnerable to timing attacks even if hashing were enabled.

A secondary **log injection / CRLF (CWE-117)** vulnerability exists in `session.js` where the raw `userName` value is passed to `console.log()` without newline sanitization, but this is evaluated as **Medium** severity and does not affect the CVSS score above.

## Vulnerability Details

### 1. Plaintext Password Storage — `addUser()`

```js
// app/data/user-dao.js  ~line 28
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password   // ← raw plaintext stored directly in MongoDB
    /*
    // Fix for A2-1 - Broken Auth  ← INTENTIONALLY DISABLED
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())
    */
};
```

Every password written to the `users` collection is cleartext. `bcrypt` is imported but never called on the write path.

### 2. Direct Equality Password Comparison — `comparePassword()`

```js
// app/data/user-dao.js  ~line 55
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;   // ← plaintext vs plaintext, timing-unsafe
    /*
    return bcrypt.compareSync(fromDB, fromUser);   // DISABLED
    */
};
```

Because `===` is not a constant-time operation and performs no hashing, this is both semantically wrong (broken once hashing is restored) and vulnerable to timing side-channels.

### 3. NoSQL Injection — `validateLogin()`

```js
// app/data/user-dao.js  ~line 72
// userName arrives directly from req.body with no type assertion
usersCol.findOne({ userName: userName }, validateUserDoc);
//                           ^^^^^^^^
//  If userName = {"$gt": ""}, MongoDB matches the first document
//  in the collection — typically the first registered (admin) user.
```

No middleware strips MongoDB operators from request bodies before this point.

## Proof of Concept

### PoC 1 — Username Enumeration via NoSQL Injection

```bash
# Differentiated error responses leak whether a username exists
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": {"$regex": "^admin"}, "password": "wrongpassword"}'
# Response when user EXISTS:    "Invalid password"
# Response when user NOT found: "Invalid username"
```

The `err.noSuchUser` vs `err.invalidPassword` distinction in `handleLoginRequest()` is surfaced to the caller, making this a reliable oracle for username enumeration.

### PoC 2 — Direct Credential Harvest (DB Read Access)

```js
// After any MongoDB read access (backup, secondary vuln, open port):
db.users.find({}, { userName: 1, password: 1 })
// Returns:
// { "userName" : "admin",   "password" : "Admin_1234" }
// { "userName" : "user1",   "password" : "hunter2"   }
// ...all credentials in cleartext, immediately usable
```

### PoC 3 — Log Injection (Medium, Secondary)

```bash
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": "legituser\nERROR: Admin password reset by root", "password": "x"}'
# console.log writes the injected newline verbatim to application logs
```

**Full patched `validateLogin` function for reference:**

```js
this.validateLogin = (userName, password, callback) => {

    // Guard: reject non-string inputs to block NoSQL operator injection
    if (typeof userName !== "string" || typeof password !== "string") {
        const inputError = new Error("Invalid input");
        inputError.invalidInput = true;
        return callback(inputError, null);
    }

    // Constant-time bcrypt comparison
    const comparePassword = (hashedFromDB, fromUser) => {
        return bcrypt.compareSync(fromUser, hashedFromDB);
    };

    const validateUserDoc = (err, user) => {
        if (err) return callback(err, null);

        if (user) {
            if (comparePassword(user.password, password)) {
                callback(null, user);
            } else {
                const invalidPasswordError = new Error("Invalid password");
                invalidPasswordError.invalidPassword = true;
                callback(invalidPasswordError, null);
            }
        } else {
            const noSuchUserError = new Error("No such user");
            noSuchUserError.noSuchUser = true;
            callback(noSuchUserError, null);
        }
    };

    // userName is now guaranteed to be a plain string
    usersCol.findOne({ userName: userName }, validateUserDoc);
};
```

## Additional Hardening

1. **Global NoSQL sanitization middleware** — Install and mount `express-mongo-sanitize` before any route handler to strip `$` and `.` keys from all request bodies and query strings:
   ```js
   const mongoSanitize = require('express-mongo-sanitize');
   app.use(mongoSanitize());
   ```

2. **Existing plaintext password migration** — Force a re-hash on next successful login:
   ```js
   // After verifying plaintext match during transitional login:
   if (!user.password.startsWith('$2')) {   // not yet bcrypt
       usersCol.updateOne({ _id: user._id },
           { $set: { password: bcrypt.hashSync(password, bcrypt.genSaltSync(10)) } });
   }
   ```

3. **Increase bcrypt work factor** — Use a cost factor of at least **12** (current `genSaltSync()` default is 10). Benchmark on target hardware; OWASP recommends ≥10 with a target of 1 second per hash.

4. **Log injection remediation** (`session.js`) — Strip CR/LF from `userName` before logging:
   ```js
   const safeName = userName.replace(/[\r\n]/g, '_');
   console.log("Error: attempt to login with invalid user: ", safeName);
   ```

5. **Generic authentication error responses** — Consider unifying the `noSuchUser` and `invalidPassword` error paths in `handleLoginRequest()` to return a single `"Invalid username and/or password"` message to the end user, removing the username enumeration oracle (while keeping differentiated internal logging).
