## Summary

Three compounding vulnerabilities in the authentication subsystem combine to create a Critical-severity exploit chain:

1. **Plaintext password storage** — `bcrypt.hashSync()` is commented out in `addUser()`; passwords are persisted to MongoDB in cleartext.
2. **NoSQL operator injection** — `validateLogin()` passes the raw, unsanitized `userName` value directly to `usersCol.findOne()`. When the application uses a JSON body parser (the default in Express), a POST body containing `{"userName": {"$gt": ""}, "password": "x"}` is deserialized to a MongoDB operator object and matches the first user document in the collection, granting authentication bypass with zero credential knowledge.
3. **Log injection (CRLF)** — `handleLoginRequest()` writes the raw `userName` to `console.log` without encoding; the ESAPI mitigation is commented out.

No rate-limiting or account lockout is present anywhere in the login flow, enabling unrestricted automated exploitation.

## Vulnerability Details

### 1 — Plaintext Password Storage (CWE-256)

**`app/data/user-dao.js` — `addUser()`**

The bcrypt hashing call is explicitly commented out and replaced with the raw request parameter:

```js
const user = {
    userName,
    firstName,
    lastName,
    benefitStartDate: this.getRandomFutureDate(),
    password //received from request param
    /*
    // Fix for A2-1 - Broken Auth
    password: bcrypt.hashSync(password, bcrypt.genSaltSync())
    */
};
```

Every password in the `users` collection is stored as a cleartext string. Any read access to the database — via injection, misconfiguration, or lateral movement — immediately exposes all credentials with zero cracking effort, enabling large-scale credential-stuffing attacks against external services.

### 2 — Direct String Equality Password Comparison (CWE-256)

**`app/data/user-dao.js` — `validateLogin()` → `comparePassword()`**

```js
const comparePassword = (fromDB, fromUser) => {
    return fromDB === fromUser;
    /*
    // Fix for A2-Broken Auth
    return bcrypt.compareSync(fromDB, fromUser);
    */
};
```

Because stored passwords are plaintext, `===` comparison accidentally works for normal logins — but it is not constant-time, introduces a timing side-channel, and makes the entire scheme collapse once the plaintext store is accessed.

### 3 — NoSQL Operator Injection (CWE-943)

**`app/data/user-dao.js` — `validateLogin()`**

```js
usersCol.findOne({ userName: userName }, validateUserDoc);
```

`userName` originates from `req.body.userName` with no type validation. When Express is configured with `express.json()` (the default), the JSON body `{"userName": {"$gt": ""}, "password": "anything"}` causes the MongoDB query to become `{ userName: { $gt: "" } }`, which matches the first document in the collection. The returned user document passes the `comparePassword` check because the attacker can supply the plaintext password (obtained via a prior injection or guessed) or because the injection returns an admin document whose password the attacker already knows.

### 4 — Log Injection / CRLF Injection (CWE-117)

**`app/routes/session.js` — `handleLoginRequest()`**

```js
console.log("Error: attempt to login with invalid user: ", userName);
// ESAPI encoding fix is commented out
```

A `userName` value containing `\r\n` sequences allows forging of additional log lines, enabling an attacker to obscure malicious activity or frame legitimate users in audit logs.

## Proof of Concept

### Authentication Bypass via NoSQL Injection

Requirements: application reachable over HTTP, `express.json()` body parser active (default).

```bash
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": {"$gt": ""}, "password": "irrelevant"}'
# Expected result: HTTP 302 redirect to /dashboard — logged in as first user in DB
# (typically the admin account seeded during initialisation)
```

### Plaintext Credential Extraction

If an attacker obtains any MongoDB read access:

```js
db.users.find({}, { userName: 1, password: 1 })
// Returns: { userName: "admin", password: "Admin_123" }
// All passwords immediately usable — no hashing to defeat
```

### CRLF Log Injection

```bash
curl -s -X POST http://localhost:4000/login \
  -H 'Content-Type: application/json' \
  -d '{"userName": "admin\r\nINFO: Login succeeded for user: admin", "password": "x"}'
# Server logs will contain a forged "Login succeeded" entry
```

## Validation

- **Plaintext storage confirmed** — `bcrypt.hashSync` is explicitly commented out; `password` field populated directly from `req.body`.
- **String comparison confirmed** — `bcrypt.compareSync` is explicitly commented out; `===` used against stored plaintext.
- **NoSQL injection confirmed** — `usersCol.findOne({ userName: userName })` receives an unvalidated value with no `typeof` guard; MongoDB driver will interpret an object value as a query operator.
- **Log injection confirmed** — `console.log("Error: attempt to login with invalid user: ", userName)` writes raw input; ESAPI mitigation commented out.
- **No rate limiting** — no `express-rate-limit` or equivalent middleware visible in session handler or any referenced middleware chain.
- **Confidence:** High — all code paths are directly reachable from the unauthenticated `/login` POST endpoint.

**Mitigating factors (minimal):** NoSQL injection requires a JSON body parser to be active; URL-encoded-only configurations are partially protected. Log injection has no direct account-compromise impact. Neither factor reduces the overall severity of the plaintext storage finding.

```diff
@@ -63,6 +63,16 @@ function UserDAO(db) {
         };
 
-        usersCol.findOne({ userName: userName }, validateUserDoc);
+        // Sanitize userName: enforce string type to prevent NoSQL operator injection
+        // (Fix for CWE-943 NoSQL Injection)
+        if (typeof userName !== "string" || !userName) {
+            const invalidUserError = new Error("No such user");
+            invalidUserError.noSuchUser = true;
+            return callback(invalidUserError, null);

```

**Key changes:**

| # | Change | Fixes |
|---|---|---|
| 1 | `bcrypt.hashSync(password, bcrypt.genSaltSync(10))` in `addUser()` | CWE-256 — plaintext storage |
| 2 | `bcrypt.compareSync(fromUser, fromDB)` in `comparePassword()` | CWE-256 — plaintext comparison, timing side-channel |
| 3 | `typeof userName !== "string"` guard + `String(userName)` in `findOne` | CWE-943 — NoSQL operator injection |

> ⚠️ **Note on argument order:** `bcrypt.compareSync(plaintext, hash)` — the plaintext is the first argument and the stored hash is the second. The original commented-out code had these reversed, which would have caused all logins to fail. The patch corrects this.

## Additional Hardening

1. **Rate-limit the `/login` route** — add `express-rate-limit` with a maximum of 10 attempts per 15 minutes per IP to prevent brute-force and injection fuzzing:
   ```js
   const rateLimit = require('express-rate-limit');
   const loginLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 10 });
   app.post('/login', loginLimiter, sessionHandler.handleLoginRequest);
   ```

2. **Sanitize `userName` before logging** — strip or encode CR/LF characters to prevent log injection:
   ```js
   const safeUserName = userName.replace(/[\r\n]/g, '_');
   console.log("Error: attempt to login with invalid user: ", safeUserName);
   ```

3. **Increase bcrypt work factor** — use at least 12 rounds in production environments for adequate resistance to GPU-accelerated offline cracking.

4. **Re-hash existing passwords** — after deploying this fix, existing plaintext passwords in the database must be migrated. On next successful login, re-hash using the new code path before committing the session.

5. **Schema validation** — apply MongoDB schema validation (JSON Schema) on the `users` collection to enforce `userName` as a string type at the database level as a defence-in-depth measure.
